# 设计与运行语义

本文件记录采集、去重、发送与故障恢复的约定，便于维护时检查行为是否发生变化。

## 分工

```text
Go 主进程
 ├─ 单实例文件锁
 ├─ 顺序采集循环 → Python 子进程 → twscrape → X
 │                 stdout: 单个 JSON，stderr 不转存
 ├─ SQLite：帖子、上下文缓存、采集进度、每帖子/目标卡片队列、故障状态
 └─ 每个启用目标独立 worker → 飞书 Webhook
```

Python 不是常驻 HTTP 服务；每次采集都是有超时上限的子进程。Python 不拥有业务去重状态；Go 在一次数据库事务中保存帖子、发送任务和分页进度，避免“抓到但没有入队”后丢失。

## 采集状态

- `baseline`：首次有效采集的开始时刻，此前发布的历史帖子不推送。请求失败不初始化。
- `last_request_success`：最近一次成功取得有效头页的开始时刻。
- `last_complete`：最近一次从头扫描确认达到目标窗口边界的开始时刻；不因部分分页而更新。
- `cursor / scan_since / scan_started`：未完成扫描的续页和固定窗口。续页跨轮保持窗口不动，防止每次推进时间边界而丢弃中间数据。

没有新帖子与没有取到有效数据是两回事。超时或部分抓取的有效内容可以先持久化，但完整进度保持原值。长时间停机或过期续页超过自动补抓窗口，会明确通知未覆盖区间的风险；窗口外尚未抓到的内容不自动刷群。

只刷新一个最新头页并接续旧游标，不能证明这期间新增的多页内容已经全部覆盖。因此续页到达边界后会安排从头复核，不能直接将整个窗口标成完整。X 返回内容本身仍可能受可见性、删除、排序或接口限制影响。

## 发送状态

- 帖子 ID 与发送任务去重键分离。任务键包含帖子 ID、目标稳定 ID；旧分片序号字段保留兼容性，新帖子只创建序号 0 的一张卡片。
- 每条帖子/回复独立一张 Card 2.0，不合并多条新增，也不将长帖拆成多张卡。队列保存结构化原文；发送时生成卡片并按最终 JSON 字节预算截断预览，保留明确提示和原帖链接。
- 每个目标独立排队；单个目标按已知发布时间从旧到新处理，告警优先，调试卡片最低优先级。
- 启动时将旧普通帖子仍未完成的分片合并为一张卡片，保留第一条未完成任务的 ID、重试时间和尝试次数，其余未完成分片标记为 superseded；已成功记录不变。
- 发送前持久记录尝试次数、限速时间；只有 HTTP 与业务响应都确认成功后才标为已发送。
- 不设置易丢失的纯内存“已发送”状态，也不把超时当成成功。
- 未确认发送在进程崩溃后仍为待发送，可能重复，但不静默丢弃。
- 永久配置错误暂停该目标，重启解除暂停；临时错误保留任务并退避。
- 服务端较长的冷却时间适用于整个目标，告警也不能绕过它。

新增目标不补旧帖子；禁用目标不创建新任务；重新启用继续原有积压。前缀和签名在每次尝试时应用，URL/密钥变更不改变任务身份。

## 告警与凭据

采集失败、覆盖不完整和发送失败分别记录故障状态；达到阈值并经过冷却后才创建告警任务，恢复后只创建一次恢复通知。永久发送配置错误立即提醒其他可用目标；失败的告警不递归生成告警。

业务库不保存 Webhook、签名密钥或账号 Cookie。凭据只在配置与进程环境中出现，HTTP 错误不包含原始 URL/响应文本。Python 错误只跨进程传递固定类别，防止上游异常带出账号或代理密码。

## 不在初版范围

- 图片上传、翻译、摘要、重置事件识别。卡片仅做展示和打开原帖，不实现交互回调。
- Web UI、Docker、群内命令、飞书应用机器人。
- 自动登录、验证码处理、通过重置锁或切换账号绕过限流。
- 自动修改已有账号库权限、启动自动测试推送、自动安装或启动系统服务。
- 热加载、多实例高可用、严格跨网络恰好一次。
